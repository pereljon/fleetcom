## 2026-09-13 - Timestamps computed in Go (`time.RFC3339`), never via SQLite `datetime()`
Why: `ClaimItem`'s atomic-claim `UPDATE` originally computed `claim_expires_at` with SQLite's `datetime(?, '+N minutes')`, which outputs `YYYY-MM-DD HH:MM:SS` (space separator, no `Z`), while `nowISO()` produces RFC3339 (`T` separator, `Z` suffix). String-compared, the space sorts before `T`, so `claim_expires_at < :now` was always true and every claim looked expired — the concurrent-claim test (`TestClaimItem_ConcurrentClaims_OnlyOneWins`) caught 10/10 goroutines winning instead of 1. Fixed by computing `claim_expires_at` in Go (`time.Now().UTC().Add(...).Format(time.RFC3339)`) so every timestamp column shares one sortable format.
Rejected: formatting the SQL `now` parameter to match SQLite's `datetime()` output instead — rejected because it leaves a second timestamp convention alive in the codebase, more surface area for the next occurrence of this bug.

## 2026-09-13 - `ListItems(PoolOnly: true)` treats an expired claim as pool-visible
Why: pre-commit review found `PoolOnly` filtered on `claimed_by IS NULL` only, so a task with a stale `claim_expires_at` (crash recovery case, PDR section 4.2) stayed invisible to `fleetcom_task_list(pool_only=true)` even though `ClaimItem` would let another agent take it. Fixed the filter to `(claimed_by IS NULL OR claim_expires_at < now)`, matching `ClaimItem`'s own availability predicate. Added `TestListItems_PoolOnly_IncludesItemsWithExpiredLease` and `TestClaimItem_ExpiredLease_CanBeReclaimedByAnotherAgent`.

## 2026-09-13 - MCP server built on `github.com/modelcontextprotocol/go-sdk` (v1.7.0)
Why: it's the official Go SDK for the Model Context Protocol, supports stdio transport (`mcp.StdioTransport`) and generic typed tool handlers (`mcp.AddTool[In, Out]`) that auto-infer JSON schema from Go structs and auto-populate `StructuredContent` — matches the PDR's "Stdio JSON-RPC 2.0 (MCP protocol)" requirement (section 2.3) with minimal boilerplate.
Rejected: hand-rolling JSON-RPC framing over stdio — rejected as needless reimplementation of a spec the official SDK already implements and tests.

## 2026-09-13 - `fleetcom_task_create`/`fleetcom_event_create` take an `agent_id` param not in the PDR's literal tool signature
Why: `dev/IMPLEMENTATION-SPEC.md` section 5.1/5.2 lists `fleetcom_task_create(summary, description, due, priority, target_agent)` and `fleetcom_event_create(summary, dtstart, dtend, description)` with no creator/caller field, but `office_items.created_by` is `NOT NULL REFERENCES agents(agent_id)` (section 3.2) — the schema requires a creator that the PDR's tool signature never supplies. Added a required `agent_id` input to both tools to satisfy the FK; this is a PDR gap, not a reinterpretation of an explicit decision.

## 2026-09-13 - Task/event UIDs are generated server-side via `github.com/google/uuid`
Why: the PDR (section 3.2) says `uid` is "UUID or nanoid" but neither the schema nor the tool signatures say who generates it. Generating in the MCP handler (`uuid.NewString()`) rather than asking the caller to supply one avoids collision risk from multiple agents picking their own ids, and matches `google/uuid` already being pulled in transitively by the SQLite driver chain.

## 2026-09-13 - Full restart: Go implementation removed, rebuilt in Python as four minimal "office primitives"
Why: jP confirmed directly in chat that the PDR (`dev/IMPLEMENTATION-SPEC.md` v1.2.0: atomic task-lease queue, RFC-2119 policy engine, agent directory/heartbeat, unified `office_items` table) drifted from the original day-to-day intent during the research phase. The real problem (per `INTENT.md`, provided by jP): Hermes profiles and Claude Code sessions have no shared office data — a phone number one agent finds is invisible to others, tasks get relayed through chat, nobody has a place to check what's due, no shared address book exists. That's a shared notebook, not a race-safe distributed work queue.
Brainstormed live in chat before any deletion: confirmed reminders are pull-only (no daemon/push — `ScheduleWakeup`-style active notification was explicitly ruled out), confirmed dropping the agent directory/heartbeat table entirely (owner/created_by become plain free-text strings, no FK, no registration), and confirmed four separate tables over one unified `office_items` table.
Rejected (this restart, vs. the old design): atomic compare-and-swap task claiming with crash-lease expiry — rejected as solving a problem (many untrusted competing workers) this fleet doesn't have; RFC-2119 policy table — rejected, fleet conventions already live in `CLAUDE.md`; unified `office_items` table with a `kind` enum — rejected in favor of four independent tables, simpler DDL, matches the four distinct nouns.
The prior Go code (`go.mod`, `go.sum`, `cmd/`, `internal/`) was `git rm`'d in the same working session as this decision; it remains recoverable from git history (commit `4e6d5a2` and earlier) but is not being deprecated-in-place or migrated.

## 2026-09-13 - Stack: Python + stdlib `sqlite3` + official `mcp` SDK's `MCPServer`
Why: jP specified Python over Go for the restart (`INTENT.md`), and the official `mcp` PyPI package (not the third-party `fastmcp` package) to avoid an extra dependency and stay on the SDK maintained by the protocol's own authors. `mcp>=1.0.0` resolved to 2.2.0 at implementation time, whose ergonomic decorator class was renamed from `FastMCP` (v1.x) to `MCPServer` (v2.x) — used `MCPServer` since it's the current official API, not the older tutorial-era name.
Rejected: third-party `fastmcp` PyPI package (more mature in some respects, but not "the official mcp SDK" jP named); pinning `mcp<2` to keep the `FastMCP` name — rejected as clinging to a deprecated API for naming familiarity alone.

## 2026-09-13 - Generic `crud.py` engine shared by all four entities, not four hand-written CRUD modules
Why: the four tables (`tasks`, `reminders`, `events`, `contacts`) share an identical CRUD shape (id/created_by/created_at/updated_at plus a handful of entity fields). Four independent hand-written CRUD implementations would be ~200 lines of near-duplicate code; one generic engine plus thin per-entity wrappers (`TABLE`, `FIELDS`, `FILTERS` constants) is a fraction of that and keeps each entity module to its actual specialization (`reminders.list_due`, `events.list_in_range`, `contacts.search`).
Security note tied to this choice: `crud.update`/`create`/`list_rows` build SQL with field/filter *names* interpolated directly into identifier positions (SQLite can't parameterize column names) — closed off by validating every field/filter name against a fixed `allowed: set[str]` before it touches the query string, so no caller-supplied dict of arbitrary keys can inject a column name. Verified with `test_update_unknown_field_rejected`.

## 2026-09-13 - Bug found via TDD: functions named `list` broke annotations in the same module
Why: `reminders.py` defines both `list(...)` (shadows the builtin `list`) and `list_due(...) -> list[dict]`. Python evaluates `list_due`'s return annotation using whatever `list` currently resolves to in the module namespace, and by the time `list_due` is defined, `list` has already been rebound to the CRUD wrapper function above it, causing `TypeError: 'function' object is not subscriptable` at import time. Fixed by adding `from __future__ import annotations` (PEP 563, defers all annotation evaluation to strings) to every module in `src/fleetcom/`, rather than renaming the public `tasks.list(...)`/`reminders.list(...)` API, which reads naturally from the caller's side.

## 2026-09-13 - `dict[str, Any]` return type required for MCP structured output, bare `dict` doesn't work
Why: probed the `mcp` 2.2.0 SDK directly — a `@server.tool()`-decorated function returning bare `dict` produces `CallToolResult.structured_content = None` (falls back to a JSON-text `TextContent` block only); annotating the return as `dict[str, Any]` populates `structured_content` correctly. Every tool in `server.py` uses `dict[str, Any]`, confirmed by `test_server.py` asserting on `structured_content` directly.

Why: matches the existing `github.com/metro18/orchestrator` naming, and the `metro18` SSH/GitHub identity is the one already used for `development/` Go projects on this machine.

## 2026-09-13 - Reminder merge: multi-round design review, reminders absorbed into `tasks`, not `events`, not kept standalone
Why (full reasoning in `DESIGN_REVIEW.md`, `RESULT.md`, and `HERMES_RESULT.md` -- the last two superseded by this entry now that it's implemented): jP challenged the original three-table design (tasks/reminders/events) across four exchanges.
1. `DESIGN_REVIEW.md` (answered inline in chat, no result file): first asked whether merging reminders into *tasks* loses anything. Verdict at the time: keep separate, on three grounds -- reminders' binary `done` vs. tasks' 3-state enum, reminders with no work attached ("flight lands at 3pm"), and reminders about external things (domain renewal).
2. `VTODO_CHALLENGE.md` -> `RESULT.md`: challenged the *recurrence* leg of that verdict via RFC 5545's RRULE-on-VTODO precedent (Apple Reminders repeats one object, no schema split). Conceded that leg was overstated, but the no-work-attached and external-thing arguments were untouched, so the verdict held: keep separate.
3. `HERMES_TASK.md` "Round 3" -> `HERMES_RESULT.md` (first version): proposed merging into *events* instead of tasks. Verdict: still keep separate -- the no-work-attached argument actually cuts *for* an events-merge (conceded), but Apple's real implementation pairs reminders with VTODO (the to-do type, same as tasks), not VEVENT (events), which argues the opposite of what that round's own "matches Apple's split" citation claimed.
4. `HERMES_TASK.md` "Round 4" -> `HERMES_RESULT.md` (final version, overwrote Round 3's): jP's objection -- "completion without ownership" is always one of exactly three things: creator-ownership, jP-ownership, or system delivery metadata (a timestamp, not a status), so reminders-as-a-third-category doesn't hold. Steelmanned this and found one real gap (acknowledgment/read-state of an unowned, informational notice, e.g. "FYI: vendor changed their number" -- neither ownership nor pure delivery metadata), but concluded the gap doesn't need a table: `tasks.owner` was already nullable, so "unowned task marked completed" already represents "acknowledged" without any schema change. Verdict flipped: accept the merge, into `tasks` specifically (matching the trichotomy's own framing: "notice/renew/check X at time T" is a small task).
Implemented: two tables. `tasks` absorbs reminders via a nullable `remind_at` column (independent of `due`); `events` stays unchanged (no completion concept, ever).
Rejected: keeping reminders standalone (exchanges 1-2's conclusion, superseded by exchange 4); merging into events (exchange 3); a three-tier model with reminders as a genuinely separate middle category (exchange 3's own position, reversed in exchange 4 on the ownership-nullability point).

## 2026-09-13 - Status lifecycle: add `blocked`/`blocked_reason`; split completion into `status='completed'` + separate `reviewed` boolean, not a 5-state enum
Why: a parallel design review (`DESIGN_REVIEW.md`) proposed adding `blocked` and splitting terminal completion into `done`/`reviewed` as two sequential enum values. Analysis concluded the two are orthogonal axes (is the work finished / has it been checked), not sequential points on one line — modeling both as `status` values would require the generic `crud.update` engine to enforce transition legality and actor permission, which it was deliberately never built to do (it's a blind field-setter by design). Implemented instead as: `status` enum gains only `blocked` (CHECK-enforced to require `blocked_reason`), and `reviewed` is a separate boolean column, settable only via the bespoke `tasks.accept`/`tasks.reject` functions (not part of `tasks.FIELDS`, so generic `task_update` can never touch it). `blocked` is reachable from both `open` and `in-progress` (jP decision). The `remind_at <= due` CHECK proposed during the merge review was explicitly dropped (jP decision: "post-deadline re-check alerts are legitimate").
Rejected: a `done`/`reviewed` pair of sequential status values (would need transition-legality + actor-permission logic bolted onto the generic CRUD engine, breaking the "every entity is a thin wrapper" pattern); enforcing `actor` on `accept`/`reject` as a real permission check (fleetcom has no agent-identity layer anywhere else, so this would be the first and only enforced permission in the system, backed by nothing but a self-reported string — treated as audit-trail data instead).

## 2026-09-13 - `HERMES_TASK.md`'s own tool-count arithmetic was wrong; implemented 15 tools, not the stated 13
Why: the approved task listed `task_accept`/`task_reject` under "New/changed tools" (implying they're MCP tools, which they must be to be reachable by any agent including CoS) but its "Net tool count: 17 -> 13 (4 task + 4 event + 4 contact + agenda_today)" line only counts 4 task tools, omitting the 2 it just added. Flagged in the pre-commit review rather than silently resolved either direction; implemented as 6 task + 4 event + 4 contact + 1 agenda = 15, since building `accept`/`reject` as unreachable internal-only functions would defeat their purpose.

## 2026-09-13 - Reject's note has no dedicated column; appended to `description`
Why: the approved schema for `tasks.reject(task_id, actor, note)` didn't specify where `note` is stored, and no new column was in the approved list (only `blocked_reason`, `result_summary`, `reviewed`, `remind_at`). Chose to append `f"[Rejected by {actor}]: {note}"` to the task's existing `description` rather than invent an unapproved column or silently drop the note. This mutates `description` destructively (no history of prior rejections beyond what's already been appended) — acceptable for a "clean, minimal" scope but worth revisiting if rejection happens often enough that losing prior notes matters.

## 2026-09-13 - `tasks.accept` now records `actor`, matching `tasks.reject` (was previously discarded)
Why: a follow-up pre-commit review (`HERMES_TASK.md`) restated "actor recorded" as an expected invariant for both `accept` and `reject`. The prior round had `accept()` discard `actor` entirely (`del actor`) after the earlier review caught the asymmetry and "fixed" it by correcting the docstring rather than the behavior — reasonable at the time given no requirement had said otherwise, but this round's explicit restatement is the clarification needed to treat it as a real gap. `accept()` now appends `f"[Accepted by {actor}]"` to `description`, same mechanism and same limitation as `reject` (destructive append, no history). Added `test_accept_records_actor` test-first (RED: `TypeError` on a `None` description) before implementing.

## 2026-09-13 - Deployment convention: installed binary via `uv tool install`, never run from the development checkout
Why: an MCP client config (Claude Code's `~/.claude.json`, Hermes's `config.yaml`) needs a stable, absolute command path that doesn't depend on the checkout's location or on `uv run` resolving the right project from an arbitrary working directory. `uv tool install --from /Users/jonathan/Claude/development/fleetcom fleetcom` installs a `fleetcom-mcp` executable at `/Users/jonathan/.local/bin/fleetcom-mcp` whose shebang is pinned to its own isolated venv interpreter (confirmed: `#!/Users/jonathan/.local/share/uv/tools/fleetcom/bin/python`) — this sidesteps a real footgun: macOS ships `/usr/bin/python3` at 3.9.6 (confirmed on this machine), too old to import `mcp` (which needs >=3.10) or satisfy this project's own `>=3.11` floor, and an MCP client's config may not reliably run in an environment where `python3` on `PATH` resolves to a newer interpreter (Homebrew's 3.14 here) rather than Apple's bundled one. Verified the installed binary directly (not via `uv run`) answers `tools/list` (15 tools) and a real tool call over actual stdio.
DB path stays `~/Claude/-hermes/fleetcom.db` by default, overridable by `FLEETCOM_DB_PATH` or the new `--db` flag (flag wins if both given; added this round -- previously there was no CLI flag at all, only the env var, which `HERMES_TASK.md` had assumed already existed).
The fleetcom skill lives in-repo under `skills/fleetcom/` and per this decision is meant to be symlinked into the fleet's shared skills directory. That symlink was **not created** as part of this work: no path for "the fleet skills dir" was given anywhere in this session, and guessing at one risked creating a dangling or wrongly-placed symlink outside this repo. Flagged in `context/todo.md` rather than fabricated.
Rejected: running `fleetcom-mcp` via `uv run --directory <checkout>` from MCP client configs (the prior convention) -- works, but ties every client config to the checkout's absolute path and re-resolves the project on every launch instead of using a pinned, already-built environment.
