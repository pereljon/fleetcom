# SKELETON - how it works

Owns: the logic flow and key invariants of the codebase, as prose or pseudocode. Does NOT hold per-function purposes (dev/CODEMAP.md).
Maintain: update when control flow, call sequences, or invariants change.

## Logic Flow

- `fleetcom-mcp` (`server.main`) parses its arguments with `_parse_args` (`--db`, `--create-db`), opens one `sqlite3.Connection` via `db.connect(path, create=...)`, runs `db.migrate(conn)` (DDL and `schema_version` stamp, skipped when the stored version is current), runs `db.normalize_stored_times(conn)` (rewrites stored times in UTC and returns `(rows fixed, list of (table, id) left)`; `main` prints `normalized times in N rows to UTC` when it fixed any, and `could not normalize times in <table> <id>, ...` when it left any, both to stderr), builds an `MCPServer` via `server.build_server(conn)`, and runs it over stdio. The connection is opened once and closed over by every tool closure — tool functions never take `conn` as an MCP-visible parameter. When `db.connect` raises `FileNotFoundError`, another `OSError`, or `sqlite3.DatabaseError` (for example, a file that is not a database, or an existing file with no `schema_version` when `--create-db` is not set), `main` exits with status 1 and a one-line stderr message.
- Each entity (`tasks`, `events`, `contacts`) is a thin module over the shared `crud` engine: `create`/`get`/`update`/`delete` all delegate to `crud.*` with a fixed `TABLE` name and a `FIELDS` allow-set. Every list query (task listing, due-now filtering, date range, substring search) is a bespoke query written directly in that entity's module, not forced into the generic engine. `tasks.accept`/`tasks.reject` are bespoke, status-gated transitions that bypass `crud.update` entirely (see Key Invariants).
- `agenda.today(conn)` is a cross-entity aggregator: `tasks.list(due_now=True)` + `events.list_in_range` for the current UTC day. It calls into the entity modules; entity modules never call back into it.
- `server.build_server` registers 15 `@mcp.tool()` functions, each wrapped in `@_anticipated`. A tool is a straight decode-call-encode adapter: typed keyword args (auto-inferred JSON schema) -> one call into the matching entity module, wrapped in `util.capped` on list tools -> a `dict[str, Any]` return (auto-populated into `CallToolResult.structured_content` because the return type is `dict[str, Any]`, not bare `dict`).
- `_anticipated` catches `ValueError` (crud's unknown-field guard, and `crud.NotFoundError`, a `ValueError` subclass that names an unknown id, raised by `crud.update`, `crud.delete`, `tasks.accept`, and `tasks.reject`) and `sqlite3.IntegrityError` (CHECK-constraint rejections: bad status enum, blocked-without-reason, bad event date range) and re-raises as the SDK's `ToolError`. It also converts a `sqlite3.OperationalError` whose message contains `locked` into a `ToolError` that tells the caller to retry; other `OperationalError`s propagate. A `ToolError` reaches the caller with its message, while every other exception produces the generic "Error executing tool X". Applied uniformly to all 15 tools.
- `task_update` builds a `fields` dict from only the non-`None` arguments the caller passed, so calling with a subset of fields is a partial update. A field cannot be reset to null this way, except `due`, `remind_at`, and `end`: passing `""` for one of them stores null, because `util.to_utc` maps `""` to `None`.

## Key Invariants

- **No caller-controlled SQL identifiers without an allow-list.** `crud.py`'s `create`/`update` interpolate field names into the SQL text (SQLite can't parameterize identifiers), but every call site passes a fixed `set[str]` of allowed names and `crud` raises `ValueError` on anything outside it. `table` names are always literals from the calling module, never derived from input. `tasks.list` writes its filter names as literals and interpolates only its two module-level sort constants.
- **Truncation flags come first in a response.** Hermes replaces an MCP result over 50,000 characters with a 1,500-character preview, so a flag after the rows can vanish when it matters. `util.capped` detects truncation by fetching `limit + 1` rows, so list tools must pass its `limit` to the entity function.
- **Ownership has no locking.** `owner` is a plain mutable, nullable string column, and `created_by` is a required string set at creation. Two agents writing the same row race at the SQL level with last-write-wins; there is no claim/lease/expiry concept in this schema. This is intentional (see `docs/ISSUES.md` (Decisions), 2026-09-13 restart).
- **Completion has two independent axes, not one enum.** `status = 'completed'` (set by whoever did the work, via generic `task_update`) and `reviewed = 1` (set only via the bespoke `tasks.accept`, gated on `status == 'completed'`) are separate. `reviewed` is deliberately *not* in `tasks.FIELDS`, so it can never be set through generic `task_update` — the only path to `reviewed=1` is `accept`, `reject` moves a completed task back to `in-progress` and resets `reviewed` to 0, and `tasks.update` resets `reviewed` to 0 in the same `UPDATE` whenever it sets any status other than `completed`. This is why `accept`/`reject` bypass `crud.update`: the generic engine has no concept of "gate this write on the row's current state," and was deliberately not extended to have one — see `docs/ISSUES.md` (Decisions) for why a bespoke function was chosen over teaching `crud` a state-machine.
- **`blocked_reason` is enforced by a table CHECK, not application code**: `CHECK (status != 'blocked' OR blocked_reason IS NOT NULL)`. Setting `status='blocked'` without supplying `blocked_reason` in the same call still passes if the row already has a `blocked_reason` from a previous call — the constraint reads the row's final state after the UPDATE, not just the changed columns.
- **Reminders are not a separate primitive.** They were merged into `tasks` (a task with only `remind_at` set) after a design review — see `docs/ISSUES.md` (Decisions), "Reminder merge" entries. `task_list(due_now=True)` / `tasks.list(due_now=True)` uses the predicate `status != 'completed' AND (remind_at <= now OR due <= now)`. This remains pull-only — nothing in this process watches the clock or notifies anyone.
- **All modules use `from __future__ import annotations`.** Needed because several entity modules define a function literally named `list` (e.g. `tasks.list`), which shadows the builtin for the rest of that module — without deferred annotation evaluation, a later `-> list[dict]` return annotation in the same file breaks at import time (hit once during development; see `docs/ISSUES.md` (Decisions)).
- **Every stored time is a UTC string in `util.now_iso()` format** (`%Y-%m-%dT%H:%M:%SZ`). String order must equal time order, because `due_now`, `event_list`, and the events `CHECK (end >= start)` compare times as strings. Entity writes enforce it: `util.to_utc` converts one value (no offset means UTC, `""` means null, anything unparseable raises `ValueError`), and `util.normalize_times` applies it to the named fields of `tasks.update`, `tasks.create`, `events.create`, `events.update`, and `events.list_in_range`. `db.normalize_stored_times` repairs rows at every startup, because servers that have not restarted still write offset times. The exception is a row the repair could not fix, because a time is unreadable or its UPDATE breaks a constraint: startup names it by table and id on stderr and leaves its value unchanged. The repair rewrites all time columns of a row in one UPDATE guarded by the old values, so the `CHECK` holds and a concurrent write is not overwritten. Tests: `test_to_utc*` and `test_normalize_times_*` in `tests/test_util.py`, `test_normalize_stored_times_*` in `tests/test_db.py`, and `test_main_reports_normalized_and_unreadable_rows_on_stderr` in `tests/test_cli.py`; see `dev/features/utc-timestamps-tests.md`.
- **Tool calls never interleave on the shared connection.** The SDK runs sync tools in worker threads, and transactions are per connection, so `_anticipated` holds `server._call_lock` for the whole call. Without it, one call's rollback erases another call's write.
- **Every entity write runs inside `with conn:`.** A rejected statement must roll back. An open transaction holds SQLite's one write lock, and every other server process then fails with `database is locked`.
- **`db.connect` retries the switch to WAL mode.** Servers starting together on a new file (made with `create=True`) otherwise crash with `database is locked`, and the busy timeout does not cover that error. `db._enable_wal` retries only on a `locked` error, and starts no new attempt after 10 seconds. `test_servers_starting_together_on_a_new_file_all_succeed` enforces this.
- **`db.connect` never lets SQLite create a file.** A mistyped path must fail instead of starting an empty database. `connect` raises `FileNotFoundError` for a missing file unless `create=True`, and opens through a `mode=rw` URI. `test_connect_refuses_a_missing_file` enforces this.
- **`db.connect` refuses an existing file that is not a fleetcom database, and leaves it unchanged.** A path that names an empty file or another application's SQLite file must fail, and the refusal must not modify the file. Unless `create=True`, `connect` raises `sqlite3.DatabaseError` when `_stored_version` finds no `schema_version`, and it checks before `_enable_wal`, because the WAL switch would itself change the file. A fleetcom database with an older version passes, because the table exists. `test_connect_refuses_an_empty_file` and `test_connect_refuses_another_applications_database` enforce this.
- **`db.migrate` writes nothing on a current database.** A write lock held past the busy timeout would otherwise crash startup. `migrate` returns early when `_stored_version` equals `SCHEMA_VERSION`. `test_migrate_does_not_write_when_the_schema_is_current` enforces this.
