# SKELETON - how it works

Owns: the logic flow and key invariants of the codebase, as prose or pseudocode. Does NOT hold per-function purposes (dev/CODEMAP.md).
Maintain: update when control flow, call sequences, or invariants change.

## Logic Flow

- `fleetcom-mcp` (`server.main`) opens one `sqlite3.Connection` via `db.connect(db.default_db_path())`, runs `db.migrate(conn)` (idempotent DDL + `schema_version` stamp), builds an `MCPServer` via `server.build_server(conn)`, and runs it over stdio. The connection is opened once and closed over by every tool closure — tool functions never take `conn` as an MCP-visible parameter.
- Each entity (`tasks`, `events`, `contacts`) is a thin module over the shared `crud` engine: `create`/`get`/`update`/`delete` all delegate to `crud.*` with a fixed `TABLE` name and `FIELDS`/`FILTERS` allow-sets. Anything not covered by plain equality CRUD (due-now filtering, date range, substring search) is a bespoke query written directly in that entity's module, not forced into the generic engine. `tasks.accept`/`tasks.reject` are bespoke, status-gated transitions that bypass `crud.update` entirely (see Key Invariants).
- `agenda.today(conn)` is a cross-entity aggregator: `tasks.list(due_now=True)` + `events.list_in_range` for the current UTC day. It calls into the entity modules; entity modules never call back into it.
- `server.build_server` registers 15 `@mcp.tool()` functions, each wrapped in `@_anticipated`. A tool is a straight decode-call-encode adapter: typed keyword args (auto-inferred JSON schema) -> one call into the matching entity module -> a `dict[str, Any]` return (auto-populated into `CallToolResult.structured_content` because the return type is `dict[str, Any]`, not bare `dict`).
- `_anticipated` catches `ValueError` (crud's unknown-field guard) and `sqlite3.IntegrityError` (CHECK-constraint rejections: bad status enum, blocked-without-reason, bad event date range) and re-raises as the SDK's `ToolError`, which surfaces the actual message to the caller instead of the generic "Error executing tool X" every other exception produces. Applied uniformly to all 15 tools.
- `task_update` builds a `fields` dict from only the non-`None` arguments the caller passed, so calling with a subset of fields is a partial update. A field can never be explicitly reset to empty/null this way — a known, accepted limitation for a "clean, minimal" scope.

## Key Invariants

- **No caller-controlled SQL identifiers without an allow-list.** `crud.py`'s `create`/`list_rows`/`update` all interpolate field/filter names into the SQL text (SQLite can't parameterize identifiers), but every call site passes a fixed `set[str]` of allowed names and `crud` raises `ValueError` on anything outside it. `table` names are always literals from the calling module, never derived from input.
- **Ownership has no locking.** `owner`/`created_by` are plain mutable, nullable string columns. Two agents writing the same row race at the SQL level with last-write-wins; there is no claim/lease/expiry concept in this schema. This is intentional (see `context/decisions.md`, 2026-09-13 restart).
- **Completion has two independent axes, not one enum.** `status = 'completed'` (set by whoever did the work, via generic `task_update`) and `reviewed = 1` (set only via the bespoke `tasks.accept`, gated on `status == 'completed'`) are separate. `reviewed` is deliberately *not* in `tasks.FIELDS`, so it can never be set through generic `task_update` — the only path to `reviewed=1` is `accept`, and the only path back to `in-progress` from a reviewed-pending state is `reject` (which also resets `reviewed` to 0). This is why `accept`/`reject` bypass `crud.update`: the generic engine has no concept of "gate this write on the row's current state," and was deliberately not extended to have one — see `context/decisions.md` for why a bespoke function was chosen over teaching `crud` a state-machine.
- **`blocked_reason` is enforced by a table CHECK, not application code**: `CHECK (status != 'blocked' OR blocked_reason IS NOT NULL)`. Setting `status='blocked'` without supplying `blocked_reason` in the same call still passes if the row already has a `blocked_reason` from a previous call — the constraint reads the row's final state after the UPDATE, not just the changed columns.
- **Reminders are not a separate primitive.** They were merged into `tasks` (a task with only `remind_at` set) after a design review — see `context/decisions.md`, "Reminder merge" entries. `task_list(due_now=True)` / `tasks.list(due_now=True)` ports the exact predicate the old standalone `reminders.list_due` used: `status != 'completed' AND remind_at IS NOT NULL AND remind_at <= now`. This remains pull-only — nothing in this process watches the clock or notifies anyone.
- **All modules use `from __future__ import annotations`.** Needed because several entity modules define a function literally named `list` (e.g. `tasks.list`), which shadows the builtin for the rest of that module — without deferred annotation evaluation, a later `-> list[dict]` return annotation in the same file breaks at import time (hit once during development; see `context/decisions.md`).
- **Timestamps are UTC strings from `util.now_iso()`** (`%Y-%m-%dT%H:%M:%SZ`), used consistently for `created_at`/`updated_at`/comparisons, so string ordering matches chronological ordering.
